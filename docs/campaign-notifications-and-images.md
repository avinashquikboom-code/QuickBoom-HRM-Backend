# Campaign notification and image repair

## Findings and changes

- Campaign sends previously read a status then wrote SENDING without a conditional claim. Concurrent workers could both send. Rescheduling sent campaigns and resetting stale sends to DRAFT could also resend accepted pushes. Claims, edits, scheduling and cancellation now use status predicates. Stale or interrupted dispatches become DELIVERY_UNKNOWN; completed/error/unknown sends cannot be blindly replayed. This favors avoiding duplicates: an operator must investigate uncertain outcomes rather than automatically resend. FCM does not supply an exactly-once guarantee.
- FCM always received a relative webpush link, although FCM web links require HTTPS. It now receives a link only when HTTPS is provided. Repeated full campaign text also risked the 4096-byte payload limit; pushes now carry a short preview and campaign ID. Full details come from the recipient-scoped mobile endpoint.
- A tapped campaign previously fell through to a generic notification screen. The mobile app now loads the exact persisted campaign notification, marks it read, displays the image and full text, and leaves external links as explicit actions. Existing foreground local display, Android channels/permission request, background OS rendering, pending authentication, and terminated-app handling remain in use.
- Legacy token registration paths could leave another user's active token rows, and logout could leave Device rows eligible for pushes. All registration paths now share a serialized ownership transfer; logout removes/deactivates both stores. Invalid-token retirement remains in the existing Firebase service. Audience selection now excludes inactive users, fails closed for empty selected audiences, and retains creator store/branch scope during scheduled sends. This schema has employee audiences, no customer model or user/company membership relation; company-level targeting cannot be inferred from the unused Campaign.companyId field.
- The previous campaign upload wrote original bytes to randomly named local files. AWS Settings values were never used by this upload path. No existing AWS SDK/upload implementation existed in this checkout. The new backend adapter uses getIntegrationSettings (including the saved Settings fields) and the AWS SDK; it never sets a public ACL.
- Images are decoded and validated (JPEG/PNG/WebP/GIF only, 5 MiB input, 25 million pixels), flattened/rotated, stripped of metadata and encoded as optimized JPEG. GIFs use their first frame. Variants fit inside 1600, 800 and 320 pixels; each must be <=1 MiB. Content hashes and conditional S3 writes prevent duplicate objects and versions. One fixture shrank from 60,724 bytes to 8,253 bytes across all three variants; this is illustrative, not a general compression guarantee.
- CampaignImageAsset stores the canonical S3 URI, object key and bucket. APIs issue fresh signed URLs (24 hours), normalize submitted signed URLs to canonical keys, and never save expiring signatures. Existing local URLs still work. Without a configured bucket, local storage remains available.
- A ledger entry is committed before uploading, so partial/abandoned uploads remain discoverable. Failed uploads do not replace the campaign image. Database assignment validates object existence; old images remain until the replacement database update commits and subsequent GC finds no references. Hourly GC uses a seven-day grace period, checks campaign AND notification references, only handles managed keys, and retries failures. It does not delete legacy/external objects. Shared notification history deliberately keeps images alive after permanent campaign deletion. Permanent deletion is available at DELETE /api/v1/admin/campaigns/:id.

## Deployment

1. Install backend dependencies and use a Node version supported by the locked AWS SDK and Sharp packages (Node 20.9+).
2. Apply `npx prisma migrate deploy` before starting the changed backend, then `npx prisma generate` and `npm run build`. The new migration creates CampaignImageAsset only; no existing campaign/notification data is rewritten. This migration has NOT been applied to the connected database during this task.
3. Confirm the deployed backend's AWS Settings contain the intended bucket, region and credentials (or an IAM workload role). The local database inspected during this task had no populated AWS fields in its settings row. No credential values were printed or changed.
4. Allow s3:GetObject, s3:PutObject and s3:DeleteObject on the managed `campaigns/v1-*` prefix. HeadObject uses GetObject permissions; returning 404 for absent objects may also require appropriately scoped s3:ListBucket. If the bucket uses KMS, grant the required key permissions. Keep Block Public Access enabled. Browser previews may require bucket CORS for the deployed admin origin. Verify account-specific IAM/KMS policy before rollout.
5. Keep the existing Firebase credential/project configuration aligned with the mobile Firebase project. Set PUBLIC_API_URL to an externally reachable HTTPS URL for legacy local notification images. Deploy the updated mobile app for campaign navigation.
6. Keep the campaign scheduler running. GC executes hourly at minute 17. Multiple backend workers share PostgreSQL advisory locks for managed upload/assignment/cleanup. Upload/database errors are returned and logged; object/API error logs exclude credentials and raw device tokens.

No bucket policy, ACL, lifecycle, retention or versioning changes were made. In a versioned bucket, DeleteObject creates a delete marker and retained noncurrent bytes remain billable. Audit object versions and retention/legal holds before approving a prefix-scoped noncurrent-version lifecycle rule. Legacy random-name objects need a separate reference inventory; never bulk-delete them based on filenames alone. Temporary multipart-upload lifecycle rules are unnecessary for this path (bounded PutObject uploads).

## Verification

Passed: backend production TypeScript build; admin Next production build (configuration skips type validation); targeted Flutter analysis; 23 existing mobile notification navigation regression tests; `npm run test:campaigns` (mocked DB/FCM/S3 integration plus real Sharp encoding and real AWS SDK command/signature construction).

Campaign regressions cover concurrent dispatch, duplicate device-store tokens, compact payloads, invalid web links, sent-campaign reschedule/retry guards, uncertain provider outcomes, actual image format/size validation, variant dimensions, identical-image reuse, canonical/signed URL round trips, private S3 writes, conditional writes, shared campaign/notification references and eventual unreferenced cleanup. AWS network responses are simulated; the tests do not prove IAM access or actual handset delivery.

Still requires a deployed/staging acceptance run with authorized test recipients: create/publish from admin; confirm foreground/background/terminated receipt on a physical phone; tap and verify the exact campaign; replace an image and confirm references; permanently delete a campaign and verify history/shared-reference retention; verify eventual GC after grace; compare S3 object/version counts after identical uploads; inspect provider rejection and scheduler logs. No production pushes, real S3 uploads/deletions, or retention changes were performed.
