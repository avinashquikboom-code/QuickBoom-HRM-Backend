# RKD visibility after HR approval

## Confirmed defects

1. The shared /api/employee router admitted EMPLOYEE/HR/admin roles but omitted SALESMAN. The RKD submission router had already been moved ahead of it, so sales users could submit RKD while GET /api/employee/wallet still returned 403. Earlier controller-only wallet tests bypassed this role gate. SALESMAN now has access through the existing authenticated employee router; controllers continue deriving ownership from the token.
2. The wallet screen kept salary-slip JSON in a separate state object. Pull-to-refresh and commission events did not refresh it. RKD approval emits a notification, not a commissionUpdate event, so an already-open wallet could remain stale. The screen now refreshes both APIs on relevant notification envelopes, commission updates, app resume, pull-to-refresh and return from the RKD screen.
3. If approval persisted but draft recalculation failed, retrying approval skipped the refresh because changed=false. It now retries the unlocked draft refresh while keeping the approval, ledger entry and approval notification idempotent. The approval response reports the persisted inclusion flag after a successful refresh instead of its stale pre-save value.
4. Approvals held for manual adjustment had no explanation in the salary slip. They now appear as pendingRkdAdjustments metadata for the approval period and render outside earnings totals. Finalized amounts remain unchanged, consistent with the user's earlier explicit decision to await manual adjustment.

The existing RKD calculator, snapshot binding, separate RKD Incentive amount and wallet earning projection were already present. This fix addresses the surrounding authorization, refresh/recovery and rendering paths rather than creating a second credit.

## Ownership, approval, period and expense handling

- RKD HR routes now also enforce pa-commission through the existing approver permission middleware, matching notification recipient authorization.
- GET /api/salary/slip now requires authentication, checks the requested employee belongs to a non-HR caller, rejects malformed employee/period inputs, and no longer falls back to an unrelated employee when a profile is missing. Existing HR/admin/store-manager reviewer roles can select an employee.
- Approval keeps the existing authoritative request amount, reviewing HR identity and timestamp. Its IST approval month remains the payroll period unless already finalized.
- Approved earnings allocated to an unlocked draft are recalculated and saved through the existing shared payroll service. The usual saved request/payroll references prevent duplicate accounting.
- Existing Approved/Paid/Disbursed/Completed slips remain finalized. A later approval is shown awaiting manual payroll adjustment, not silently added to net salary. Legacy approved requests with no allocation remain manual-adjustment earnings. If a legacy request lacks an approval timestamp, the wallet can show it but its period cannot be safely inferred for a salary-slip notice.
- RKD is not an Expense record or reimbursement. The RKD service writes its existing commission audit mirror, the payroll calculator excludes that mirror from ordinary commission, and the wallet projects the authoritative approved RKD request. Expense reimbursements and pending claims remain separate. No extra WalletTransaction or withdrawable-balance increment is created.
- Approval notifications mean payroll eligibility only. Salary availability notifications remain tied to successful publication/update. No wallet-credit/payment notification is emitted without the corresponding payment/cash transaction.

## Limits

Backend responses and the shared mobile salary/wallet widgets are verified locally using synthetic HTTP fixtures and mocked persistence/FCM. This is not a physical-device test against the affected production employee or proof of real PostgreSQL concurrency and Android notification delivery. The new code must be reviewed and deployed through the authorized process before the affected runtime can be confirmed. Historical unallocated/finalized RKD still requires the chosen manual adjustment/reconciliation; this change makes that state visible and does not recredit it automatically.
